# Моделирование динамического поведения «Автоучёта» с помощью UML

## Контекст и постановка задачи

Для desktop-приложения «Автоучёт» уже зафиксированы требования в SRS и системный дизайн в SDD / ADR. Перед реализацией нужно однозначно описать динамическое поведение: кто инициирует сценарии, в каком порядке выполняются шаги добавления расхода, какие состояния проходит запись расхода и как пакеты UI, domain и storage обмениваются сообщениями при сохранении журнала.

Вопрос: какие UML-диаграммы и связи выбрать, чтобы покрыть ключевые сценарии MVP без избыточной детализации?

Связанные артефакты: `srs.md`, `sdd/avtouchet-sdd.md`, `docs/glossary.md`, `docs/supplementary-specs.md`, `приложения/uml/`.

## Драйверы решения

* Трассировка к функциональным требованиям SRS (REQ-FUNC-001 … REQ-FUNC-009)
* Понятность для разработки и проверки сценариев
* Соответствие согласованному MVP: один автомобиль, локальный JSON, без сети и без ИИ
* Минимально достаточный набор диаграмм лабораторной работы № 5

## Рассмотренные варианты

* Полный набор структурных и поведенческих диаграмм UML
* Только текстовые сценарии без UML
* Набор из 4 поведенческих диаграмм: Use Case, Activity, State, Sequence

## Итог решения

Выбранный вариант: «набор из 4 поведенческих диаграмм», потому что он покрывает контекст, алгоритм, состояния и взаимодействие и напрямую связан с требованиями MVP «Автоучёта».

### Последствия

* Хорошо, потому что поведение системы формализовано до кодирования
* Хорошо, потому что есть явная связь от SRS к сценариям и к PNG в `приложения/uml/`
* Нейтрально, потому что структурные диаграммы классов уже частично заданы в SDD и не дублируются здесь
* Плохо, потому что потребуется поддерживать PNG-диаграммы при изменении требований

### Подтверждение

Соблюдение решения проверяется наличием диаграмм в `приложения/uml/`, согласованностью с `docs/supplementary-specs.md` и этим ADR.

## Плюсы и минусы вариантов

### Полный набор UML-диаграмм

* Хорошо, потому что покрывает почти все точки зрения
* Плохо, потому что избыточен для локального журнала без сети

### Только текстовые сценарии

* Хорошо, потому что быстро писать
* Плохо, потому что хуже читается взаимодействие и состояния

### 4 поведенческие диаграммы

* Хорошо, потому что закрывает ключевые сценарии MVP
* Хорошо, потому что соответствует viewpoint динамики в SDD (VIEW-006, VIEW-008)
* Нейтрально, потому что не заменяет структурный дизайн целиком

## Дополнительная информация

Механизмы построения и связи:

* Use Case задаёт актёра «Пользователь» и прецеденты MVP; `include` — для проверки ввода при добавлении и изменении расхода (`приложения/uml/use-case.png`)
* Activity детализирует поток «Добавить расход» и ветвления ошибки ввода / сбоя записи (`приложения/uml/activity-add-expense.png`)
* State описывает жизненный цикл записи расхода: черновик, ошибка, сохранён, редактируется, удалён (`приложения/uml/state-expense.png`)
* Sequence показывает обмен сообщениями UI → Domain → LedgerStore и ветку `alt` при сбое записи (`приложения/uml/sequence-save-expense.png`)
